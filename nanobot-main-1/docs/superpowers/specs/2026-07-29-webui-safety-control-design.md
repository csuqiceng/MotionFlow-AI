# WebUI 安全控制闭环设计

## 目标与边界

本阶段完善 WebUI 的急停、暂停、继续、报警复位、结束当前、解除急停和解除取消操作。目标是让操作员只能看到当前状态下可执行的动作，并在执行后得到与控制器状态一致的反馈。

本阶段不改变 ZMotion 的写入协议、PLC 功能号 104 的参数映射，也不实现旧 HMI 的“复位0”或独立 X84 至 X87 位控制。它们的 PLC 语义尚未确认。

## 方案选择

可选方案如下：

1. 仅调整按钮文案和提示。改动小，但不能避免无效操作或误报成功。
2. 在 `RobotSidePanel` 中直接添加条件和提示。交付快，但会继续扩大页面组件职责。
3. 提取安全动作领域模块、状态判定模块和展示组件。页面只负责组合，动作规则可单测，后续增加控制器能力时不需要改动 UI 布局。采用此方案。

## 架构

- `robotSafety/types` 定义动作、状态快照、按钮可用性及结果的稳定类型。
- `robotSafety/policy` 是纯函数：根据状态输出每个动作的可用性、禁用原因、执行后提示和是否需要刷新验证。
- `robotSafety/useRobotSafetyActions` 只负责调用现有 transport、处理请求期间的互斥、刷新状态并将 transport 结果转换为领域结果。
- `RobotSafetyControls` 只渲染控制按钮及说明，不访问 transport，也不理解 ZMotion 写入参数。
- `RobotSidePanel` 组合状态卡、姿态卡、关节角度卡和 `RobotSafetyControls`。

模块之间仅通过类型和回调通信。控制器协议继续留在后端 `zmotion_write_plan.py`，前端不复制功能号或参数值。

## 状态与动作规则

安全动作基于服务器返回的已确认状态显示：

| 动作 | 可用条件 | 结果反馈 |
| --- | --- | --- |
| 急停 | 未急停 | 执行后刷新，确认急停状态 |
| 解除急停 | 已急停 | 说明“解除请求已发送，仍需报警复位”；不得显示为已恢复 |
| 暂停 | 未暂停且未急停 | 执行后刷新，确认暂停状态 |
| 继续 | 已暂停且未急停 | 执行后刷新，确认暂停已解除 |
| 报警复位 | 存在报警或急停恢复流程中 | 执行后刷新，确认报警清除且控制器就绪 |
| 结束当前 | 非空闲任务 | 执行后刷新，确认取消锁存 |
| 解除取消 | 存在取消锁存 | 执行后刷新，确认取消锁存已解除 |

请求运行期间全部安全操作互斥，按钮显示进行中状态。网络或后端报错保留现有错误信息，并在刷新失败时明确指出状态未确认。

## 数据流

1. `RobotSidePanel` 获取机器人状态并传给安全 hook。
2. `policy` 从状态生成操作模型。
3. 展示组件根据操作模型渲染，禁用按钮同时显示原因。
4. hook 调用既有 `robotSystemAction` 传输链路。
5. hook 刷新状态，以实际状态而非请求返回值决定最终成功提示。

解除急停和解除取消是请求释放，不是恢复完成；只有后续状态确认后才显示恢复完成。该规则消除当前“已执行”与控制器仍报警不一致的问题。

## 错误处理与测试

- 对策略模块编写表驱动单元测试，覆盖急停、暂停、报警、取消锁存、空闲和状态缺失。
- 对 hook 使用现有前端测试方式验证：请求期间互斥、成功后刷新、刷新失败不报告已确认恢复。
- 对展示组件验证禁用状态、原因和恢复提示。
- 保持后端 ZMotion 写入映射不变；现有 Python 后端测试继续作为回归检查。

## 验收标准

1. 所有安全按钮的可用性与当前机器人状态匹配。
2. 解除类操作不会误报“系统已恢复”。
3. 运行中的请求不会并发提交第二个安全指令。
4. 页面组件不再包含动作规则或 transport 细节。
5. 新增规则以独立测试覆盖，WebUI 构建和相关后端测试通过。
